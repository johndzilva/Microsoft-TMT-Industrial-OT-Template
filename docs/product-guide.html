Product and system threat model#

The method for an IEC 62443-4-2 component (a PLC, gateway or HMI software) or an IEC 62443-3-3 system (a control system solution), using the OT Product and System template.

1 Scope→2 Draw→3 Properties→4 Anchors→5 Generate→6 Review→7 Requirements→8 Report and maintain

1. Scope and assumptions#

Write down what is in scope (the product, its interfaces, its development and update process), its intended use, and your assumptions, for example "installed in a locked cabinet in a zone with SL-T 2". Record them under File > Threat Model Information.

2. Draw the diagram#

Component model (IEC 62443-4-2)#

  • Draw a Component or Device Boundary around the product.
  • Inside it, split the product into its functions: the runtime, web interface, update service, key store and firmware image.
  • Separate functions with a Process or Privilege Boundary where isolation matters, such as containers, kernel and user space, or a safety partition.
  • Outside it, add everything the product talks to: engineers, operators, the PLCs it polls, the cloud, a USB stick.

System model (IEC 62443-3-3)#

  • Draw one IEC 62443 Security Zone per zone. Add a Safety Zone SIS, an Industrial DMZ Level 3.5 and an Enterprise or IT Zone as needed. Set the Purdue level and zone SL-T on each.
  • Connect zones with the flows that really exist. Use IEC 62443 Conduit and Internet or Untrusted Network Boundary lines for the paths between them.
  • Pick the stencil that matches each device. Its IEC 62443-4-2 component type (EDR, HDR, NDR or SAR) is fixed by the stencil.

Always#

Add a Product Supplier and Development Environment with one Software Supply and Build Pipeline flow to the product. It carries the build and code-signing threats exactly once.

3. Answer the properties#

On Answer
Each component Web interface, user accounts, stored secrets, field updates, third-party code, debug ports, physical exposure, wireless, USB, legacy platform
Each flow Protocol security, control commands, safety data, secrets, physical medium
Each data store Sensitive data, control-critical data

Answer No where something does not exist, which removes threats that cannot apply. Software stencils already fix the hardware questions to Not applicable. Every question and the threats it controls are listed in Properties.

4. One anchor flow per component#

A component's own threats, such as default passwords, unsigned firmware or missing logging, should appear once and not on every flow into it.

  • Set Threats on this Flow = All on one flow into each component, normally the most exposed one.
  • Set Without component threats on the other flows into it.

The command-line tools do this for you, and check_model.py lists what is missing. If you leave everything at Auto, you get the older 1.x behaviour, which has some repeats. See How threats are generated.

5. Generate threats#

Switch to View > Analysis View.

6. Review and score#

Go through every threat. Decide whether it applies and what already mitigates it, then score its likelihood and impact. Sort by Relevant from SL to see what your target SL requires. See Reviewing threats and scoring risk.

7. Requirements and mitigations#

Each threat names the IEC 62443-4-2 component requirements (CR, EDR, HDR, NDR, SAR) or 3-3 system requirements (SR) that address it. Use them as product requirements, test cases and certification evidence.

Stable IDs

Threat IDs such as OT-S01 or OT-T23R never change between versions, so you can reference them from requirements, test reports and risk registers.

8. Report and maintain#

Create the full report. Keep the .tm7 with the design. Update it when interfaces, protocols or the update process change, and review it at each release, as IEC 62443-4-1 practice 2 (SR-2, threat model) requires.
