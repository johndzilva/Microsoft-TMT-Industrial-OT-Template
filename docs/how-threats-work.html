How threats are generated#

TMT generates threats per data flow. Version 2.0 of the templates makes sure each threat appears once, where it belongs.

The problem#

For every flow, TMT checks every threat rule against the flow's source, its target and the flow itself. Without care, a threat about a component, such as default credentials on a PLC, would appear once for every flow into that PLC. In one real review made with version 1.3, about half of the generated threats were judged repeats or not applicable.

Families and anchors#

Every threat belongs to one family, and each family has one anchor: the only kind of flow on which TMT generates it.

Family What it is about Generated on
1 Channel Sniffing, spoofing, replay, injection on the wire Flows that cross a zone or network boundary over a network medium
2 Technology Weaknesses of the target's stencil type (web UI, HMI, OPC server, safety controller) The component's anchor flow
3 Component Lifecycle of the target: credentials, patching, firmware, debug ports, crypto, logging The component's anchor flow
4 Host Malware, OS hardening, attacker tools on a host The host's anchor flow; not on software marked Runs on a Host Shown in the Model
5 Path One attacker path: this source reaching this target (vendor access, insider, USB, cloud commands) Every flow where the path exists
6 Product lifecycle Build pipeline and code-signing compromise The Software Supply and Build Pipeline flow, once per product
7 Local boundary Isolation bypass, wiring tampering Flows crossing a Process or Privilege or Physical Access boundary, and hard-wired signals
8 Data at rest Tampering, disclosure or loss of stored data The store's anchor flow in, or one flow out of a store nobody writes to (IDs ending in R)

The switch: Threats on this Flow#

This flow property chooses which families a flow shows:

Value Channel and local boundary (1, 7) Path (5) Component, host, data at rest (2, 3, 4, 8) Use it for
Auto (default) ✓ ✓ Only if the flow crosses a trust boundary or comes from an external interactor Drawing by hand; the 1.x behaviour
All ✓ ✓ ✓ The anchor: one flow into each component
Without component threats ✓ ✓ – The other flows into that component
Component threats only – – ✓ An anchor flow whose channel is already shown elsewhere
Path threats only – ✓ – A parallel flow over a channel already shown
None – – – A flow drawn only for context

Which flow should be the anchor?

For each component, set All on the flow into it that is most exposed: the one that crosses a trust boundary or comes from outside, carries control commands, and runs over a network. Set Without component threats on its other incoming flows. In Analysis View, sort the Threat List by Title: a component threat that appears twice for the same component means a second flow still has All or Auto.

Other rules#

  • Non-network media. A flow with Physical Medium = Hardwired signal (a 4-20 mA loop, a trip input) or Local operator input is not a network channel. The sniffing and spoofing threats are skipped, and the wiring tampering threat (OT-T30, PL-T11) applies instead.
  • Specific beats generic. Where a specific threat covers an attack, the generic one steps aside. Wireless sniffing (OT-I10) replaces generic sniffing (OT-I01) on a wireless link. Safety protocol tampering (OT-T11) replaces generic tampering on safety flows. Network-device DoS (OT-D08) replaces generic DoS on switches and firewalls.
  • Properties that cannot apply are fixed. Software stencils fix the hardware questions to Not applicable, so they never generate hardware threats.
  • Scope. Assessment Scope = Out of scope on an element removes its threats. Threats on this Flow = None removes a flow's threats.
  • Data that is only read. For a store nobody writes to, such as a TPM key store, set Show Data Store Threats for Source Store = Yes on one flow out of it. Its data-at-rest threats then appear with IDs ending in R.

What this gives you#

Example 1.3 2.0
